# JMeter 测试用户资料

`users-100000.csv` 是当前容量测试的用户资料集，包含 100,000 条数据和一行表头，使用 UTF-8 编码，无 BOM。

原有 `users-5000.csv` 保留为快速校验用的小数据集；这 5,000 名用户已包含在 100,000 名用户中，两份文件不要直接拼接。

```csv
"phone","nickName","icon"
"13990000000","load-test-0",""
"13990000001","load-test-1",""
```

| 字段 | 含义 |
|---|---|
| phone | 11 位测试手机号，范围 13990000000～13990099999 |
| nickName | 用户昵称，范围 load-test-0～load-test-99999，对应数据库 nick_name |
| icon | 空字符串，与原测试用户准备逻辑一致 |

数据沿用 `SeckillLoadTestDataTest` 中的编号规则，目标为总计 100,000 名测试用户，包含原有测试用户的编号范围。后续导入时应按唯一手机号复用已有用户、补充缺失用户，避免覆盖既有用户资料。实际新增数量取决于数据库中已有的手机号。

文件不指定数据库主键、密码和时间字段。数据库主键应由 MySQL 自动生成，其余字段沿用表的默认值。生成 CSV 不会导入 MySQL，也不会创建 Redis 登录会话。

## 与 JMeter 登录 Token 的关系

现有 `seckill-order-e2e.jmx` 实际读取的是无表头、每行一个有效 Token 的 `tokens.csv`，不能将本文件直接作为 `tokensFile` 使用。

后续准备流程为：创建或复用测试用户 → 获得真实用户 ID → 创建 Redis 登录会话 → 导出对应的 Token 文件。只有写入相应登录会话的 Token 才能用于认证请求，不能用随意生成的字符串代替。

现有 `SeckillLoadTestDataTest` 按相同编号规则准备用户，并不直接读取本 CSV。它还会删除指定券已有订单并重置库存，后续执行或改造时应使用本轮专用测试券。

## 数据量适用范围

在同一张券的一人一单约束下，主数据集最多提供 100,000 次不同用户的成功下单，适合初步持续负载、阶梯加压和集中抢购测试。测试券还需要充足库存和有效活动时间。

持续测试所需用户数约为：目标下单速率 ×（预热时间＋正式测量时间），另留余量。

| 目标下单速率 | 预热＋正式测量 | 预计需要用户数 | 100,000 名用户是否充足 |
|---|---|---:|---|
| 500 次/秒 | 15＋60 秒 | 37,500 | 是 |
| 1,000 次/秒 | 15＋60 秒 | 75,000 | 是，另有 25,000 名余量 |
| 1,000 次/秒 | 15＋300 秒 | 315,000 | 否，需要继续扩充 |

不同档位若使用不同专用测试券，可以复用同一批用户；同一张券的持续成功下单场景需要持续使用未购买过该券的用户。

正常成功下单场景应共享 Token 数据源、关闭循环读取，并在数据耗尽时停止，避免复用同一用户造成重复下单拒绝。更大规模测试可延续相同规则扩展数据。

## 生成与扩容

`generate-users.ps1` 默认生成 100,000 条数据，采用逐行写入，并保留已有同名文件。它只写 CSV，不连接数据库或 Redis。

在本目录中执行下面的命令，可以为后续长时间复测生成 400,000 条数据：

```powershell
.\generate-users.ps1 -Count 400000
```

可选参数 `-StartIndex` 用于指定起始编号，`-OutputFile` 用于指定新的输出文件路径。以起始编号 0 扩充得到的大数据集会包含原小数据集，不能直接拼接使用。
