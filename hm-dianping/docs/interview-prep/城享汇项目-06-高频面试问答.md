# 城享汇项目：06. 高频面试问答与回答稿

## 使用方法

每个问题先给“短答”，用于第一轮回答；“追问展开”用于面试官继续深挖时补充。回答应结合自己的实际参与，不要逐字背诵。

## 一、项目整体

### 1. 这个项目是做什么的？

**短答：**

城享汇是本地生活点评与优惠券秒杀后端，支持验证码登录、商户检索、附近商户、签到、探店内容、关注互动和优惠券秒杀。我重点完善了高并发秒杀、RabbitMQ 可靠消息、Caffeine + Redis 二级缓存一致性、分布式限流、Snowflake ID 和性能测试。

**追问展开：**

普通业务体现 Redis 数据结构的使用，例如 GEO、Bitmap、Set、ZSet；核心工程难点集中在两条链路：秒杀从 Redis 原子受理到 MySQL 最终落库，商户更新从 MySQL 到 Redis 和多实例 Caffeine 的最终一致性。

### 2. 项目中最复杂的部分是什么？

**短答：**

不是 Lua 扣库存本身，而是 Lua 成功后到数据库落库之间的失败窗口。为此我把订单状态显式记录到 Redis Pending，通过 Confirm、Return、延迟重试、失败队列、定时重投、数据库幂等和库存恢复让链路可收敛。

### 3. 为什么不用一个分布式事务解决所有一致性？

**短答：**

Redis、RabbitMQ 和 MySQL 跨组件强事务成本高、可用性差，也不适合高并发秒杀。项目按业务语义拆分：Redis Lua 原子决定受理资格，MySQL 事务决定最终订单，消息和补偿负责两者之间最终收敛。

### 4. 项目有哪些明确边界？

**短答：**

缓存是最终一致而非强一致；登录只有验证码流程且短信为模拟；Redisson 只用于可选客户端和 MultiLock 演示；Nginx 只有静态图片目录使用痕迹；Docker Compose 没有覆盖完整 MySQL 和主 Redis 生产拓扑；性能结果是本地基准，不是生产容量承诺。

## 二、登录、附近商户与签到

### 5. 登录为什么用 Token + Redis？

**短答：**

本地 Session 在多实例中需要粘性或同步。随机 Token 对应 Redis Hash，任何实例都能解析；请求经过刷新拦截器后把 UserDTO 放到 ThreadLocal，需要登录的接口再由第二个拦截器统一校验。

**追问展开：**

请求完成必须清理 ThreadLocal，避免线程池复用造成用户信息串号。Redis 中只放用户摘要，不放完整敏感实体。

### 6. 当前登录有什么安全问题？

验证码日志模拟、登录后没有立即删除验证码、发送接口没有频控，且会话 TTL 的创建与刷新单位不一致。生产上要接短信服务、一次性消费验证码、增加发送/校验限流、统一 Duration 配置，并保护日志不泄漏验证码。

### 7. 附近商户怎么实现？

**短答：**

按商户类型建立 `shop:geo:{typeId}`，member 是 shopId。查询时用 Redis GEO 搜索 5 公里内商户并按距离排序，再把当前页 ID 批量查 MySQL，用 `ORDER BY FIELD` 保持 GEO 顺序，最后回填 distance。

### 8. GEO 为什么按商户类型分 Key？

避免先在所有商户中做空间搜索再过滤类型，缩小每次检索集合。代价是商户类型变更时要维护旧、新两个 GEO Key。

### 9. 签到为什么用 Bitmap？

一个用户一个月最多 31 个布尔状态，Bitmap 极省空间。每天用 SETBIT 写对应位，连续签到用 BITFIELD 取本月至今的位集合，再从最低位开始 `& 1` 和右移，直到遇到 0。

### 10. Bitmap 能保存签到详情吗？

不能，它只能高效表示“是否签到”。若要保存位置、奖励、补签原因等，需要数据库明细；Bitmap 可以作为快速状态和统计索引。

## 三、秒杀与 Lua

### 11. 秒杀请求的完整链路是什么？

**短答：**

AOP 限流 → Snowflake 生成 orderId → Redis Lua 校验时间、库存和一人一单，同时预扣并登记 Pending → RabbitMQ 异步投递 → 消费者事务插订单和条件扣 MySQL 库存 → 更新 Pending → 手动 ACK；失败由重试、失败队列和定时补偿处理。

### 12. Lua 中为什么把多个动作放在一起？

Redis 单命令原子，但多条命令分开执行会被并发穿插。Lua 把校验、预扣、reservation 和 Pending 登记合成一个原子单元，避免检查通过后被其他请求抢走库存，也避免扣库存后没有补偿记录。

### 13. 为什么先检查一人一单，再检查库存？

用户请求超时后重试时，即使库存已经被其他人抢完，也应先识别他已有 reservation，而不是错误返回库存不足。这样不会重复扣库存。当前服务层仍返回“已经抢到”的失败提示；若要完整请求幂等，应把原 orderId 返回。

### 14. 为什么 Redis Key 要带 `{voucherId}`？

Redis Cluster 的多 Key Lua 要求所有 Key 在同一个 slot。花括号中的 Hash Tag 决定 slot，因此同一张券的库存、活动时间、reservation 和 Pending 都带相同 `{voucherId}`。

### 15. 为什么脚本用 Redis TIME？

多应用实例的本机时钟可能漂移。用 Redis 服务端时间让活动窗口判断更统一，并且时间校验和库存预扣在同一个原子脚本内。

### 16. 如何保证不超卖？

两层防线：Redis Lua 在入口原子检查并预扣，控制受理数量；MySQL 更新使用 `stock > 0` 条件，更新失败就抛异常并回滚订单插入。前者抗高并发，后者保护最终账本。

### 17. 如何保证一人一单？

Redis reservation Hash 在高并发入口去重；MySQL `UNIQUE(user_id, voucher_id)` 是最终约束。即使消息重复或 Redis 状态异常，数据库仍拒绝第二单。

### 18. 为什么先插订单再扣 MySQL 库存？

两步处于同一事务，库存扣减失败会回滚插入。先插入还能尽早触发主键或用户券唯一索引，重复消息不再执行库存更新。也可以先扣库存再插订单，但重复消息会先做无意义更新并依赖回滚。

## 四、RabbitMQ 可靠性

### 19. RabbitMQ 如何提高可靠性？

**短答：**

生产端开启 correlated Confirm、mandatory Return，交换机/队列持久化、消息 persistent；消费端手动 ACK，失败进入 5 秒 TTL 重试队列，重试耗尽可靠转发最终失败队列，失败消费者再有限重试并进入停车队列。同时 Redis Pending 记录发送失败并由定时任务重投。

### 20. Confirm ACK 能证明什么？

只证明 Broker 接收了消息。能否路由看 Return，是否消费成功看消费者 ACK 和业务落库，磁盘及副本安全还与 Broker 持久化策略有关。

### 21. Confirm 和 Return 回调顺序不确定怎么办？

ACK 更新前会检查是否已有 ROUTE_FAILED、BROKER_NACK、CONSUMING、ORDER_CREATED 或 FAILED，避免覆盖更明确状态。但当前是先读后写，不是原子状态机；更严格的实现应使用 Lua/CAS 条件迁移。

### 22. 为什么不直接 `basicNack(requeue=true)` 重试？

立即重新入队可能形成无间隔热循环，持续占 CPU、I/O 和日志。项目 reject 到带 5 秒 TTL 的重试队列，再死信回主队列，给依赖恢复时间，并能通过 x-death 控制次数。

### 23. 数据库提交后 ACK 前宕机会怎样？

Broker 没收到 ACK 会重投。同 orderId 触发主键冲突，或者同用户同券触发唯一索引；消费者把 DuplicateKeyException 视为幂等重复并 ACK，不会重复扣库存。

### 24. Redis 预扣成功但 MQ 没发出去怎么办？

Lua 已经同时写 Pending。发送异常、Confirm NACK 或 Return 会把 orderId 放回待重投 ZSet。定时任务到期先查 MySQL，不存在才重投；达到上限后用恢复 Lua 归还库存和资格。

### 25. 为什么补偿前必须查 MySQL？

消息可能已经消费成功，只是 Confirm、网络响应或 Pending 清理丢失。直接恢复会把已售库存加回去。先查订单存在性可以把“业务已成功但状态未清理”与“确实没落库”区分开。

### 26. 库存恢复如何保证幂等？

恢复 Lua 只有在 `reservation[userId] == orderId` 时才加库存并删除 reservation。第一次成功后条件不再成立，重复失败消息不会再次加库存；旧订单也不会误删用户的新预占。

### 27. 这套系统是 exactly-once 吗？

不是。RabbitMQ 使用至少一次语义，重复消息是正常情况；项目通过数据库主键、用户券唯一索引和幂等恢复脚本实现业务效果上的去重。

### 28. Pending 在 Confirm ACK 后从 ZSet 移除，会不会无法补偿消费失败？

ZSet 主要补偿“生产投递失败”。Broker 已接收后由 durable 队列、消费重试、最终失败队列负责。Pending Hash 仍保留状态与时间用于查询；最终失败消费者会恢复 Redis。不同阶段用不同机制负责，避免同一消息被两个补偿器并发重投。

### 29. 为什么失败队列还要停车队列？

最终失败消费者本身也可能因为 Redis、数据库或反序列化问题持续失败。有限重试耗尽后转入停车队列，可以隔离毒消息，防止失败队列无限重入并影响正常故障处理。

## 五、二级缓存与一致性

### 30. 商户详情的读取顺序是什么？

Caffeine → Redis → MySQL。Caffeine 命中直接返回；Redis 命中 JSON 后写本地缓存；两层都 miss 时查 MySQL并尽力回填。不存在的数据在 Redis 写 2 分钟空字符串，正常数据用 30～40 分钟随机 TTL。

### 31. Caffeine 的核心收益是什么？

减少热点请求访问 Redis 的网络和序列化成本。100,000 次热点查询测试中，关闭本地缓存约产生 100,003 次 Redis GET，开启后只增加约 2 次；P95 从 3ms 降到 1ms，吞吐量只小幅提升。

### 32. Caffeine 如何避免单机缓存击穿？

未命中时使用 `cache.get(key, loader)`，同 JVM、同 Key 的并发加载会被合并。但它不能协调多个 JVM；Redis Key 同时过期时仍可能跨实例回源，需要分布式互斥或逻辑过期进一步保护。

### 33. 为什么用空值缓存？有什么风险？

防止同一个不存在 ID 反复穿透 MySQL。风险是恶意请求大量不同 ID 会制造很多空 Key，也有短暂“新建后仍看到不存在”的窗口；所以 TTL 较短，并可结合 Bloom Filter 和限流。

### 34. 为什么 Redis TTL 要随机？

打散批量 Key 的过期时刻，降低同一时间大量 miss 回源造成雪崩。它不能解决 Redis 整体宕机。

### 35. 商户更新如何保证缓存一致性？

商户 UPDATE 和 Outbox INSERT 在同一 MySQL 事务。后台任务领取事件后删除 Redis、清本机 Caffeine、Fanout 广播其他实例，任何失败都退避重试；首次成功后延迟约 1 秒再失效一次，最后还有短 TTL 兜底。

### 36. 为什么是最终一致，不是强一致？

数据库提交和各缓存删除不是同一个原子事务，MQ 广播和消费者执行也有延迟。方案保证失效意图可恢复，并缩短旧值窗口，但某些时刻仍可能读到旧缓存。

### 37. Outbox 解决了什么？

解决“数据库已提交但进程在发 MQ 或删缓存前宕机”的窗口。业务更新和 Outbox 事件一起提交，只要数据库事务成功，失效意图就持久存在，后续扫描任务可重试。

### 38. Outbox 多实例如何避免重复处理？

多个实例可能都查到同一到期事件，但领取时执行 `UPDATE ... WHERE id=? AND status=0`。只有一个实例更新 1 行成功。即使租约过期后重复处理，删除缓存和广播失效都是幂等的。

### 39. 延迟双删解决什么竞态？

查询线程可能在更新前读到旧数据库值，更新线程提交并第一次删缓存后，查询线程又把旧值写回。延迟第二次删除用来清理这个竞争窗口中的脏回填。

### 40. 为什么每个实例的失效队列是临时队列？

它服务于该实例内存中的 Caffeine。实例离线时本地缓存也消失，无需为它保存历史广播；重启后缓存为空。在线实例各有独立队列，Fanout 才能让每个实例都收到消息。

### 41. Redis 故障时查询怎么办？

读取失败降级到 MySQL，Redis 回填失败也不覆盖成功的数据库结果。这样提升可用性，但会把压力转移到 MySQL，所以需要限流、熔断、连接池监控和故障告警。

## 六、限流、ID 与线程池

### 42. 为什么限流用 ZSet + Lua？

ZSet 的 score 保存请求时间，可精确删除窗口外记录并统计当前窗口；Lua 使清理、计数、判断和新增原子执行，适合多实例共享。缺点是每请求一条成员，内存和 CPU 成本较高。

### 43. 限流为什么做成注解和 AOP？

限流是横切关注点。注解声明规则，切面统一解析 SpEL 和配置并执行 Lua，避免 Controller 重复代码，也支持 GLOBAL、USER、IP 多维度复用。

### 44. 300 请求/秒限流是不是整场只放 300 个？

不是。它是长度 1 秒的滑动窗口，随着时间前移会继续放行。900 请求若分散在 3 秒，多数仍可能通过限流，库存耗尽后返回库存不足。

### 45. 为什么订单 ID 用 Snowflake？

异步下单在写数据库前就需要全链路 ID。Snowflake 本地生成，不依赖数据库自增或 Redis 网络调用，趋势递增且适合多实例。前提是不同实例分配不同 worker/datacenter 组合，并处理时钟与前端精度问题。

### 46. 为什么统计任务要在事务提交后执行？

避免订单事务回滚后仍被统计。`AFTER_COMMIT` 监听器只在真正提交后把任务交给线程池，统计失败也不影响已完成订单。

### 47. 线程池参数和拒绝策略是什么？

核心 4、最大 8、有界队列 200、空闲 60 秒、CallerRunsPolicy。核心线程满后先排队，队列满再扩到 8，全部满时由 RabbitMQ 消费线程执行轻量统计，形成背压并尽量不丢任务。

### 48. CallerRunsPolicy 有什么代价？

会占用提交线程，使消费者 ACK 变慢。项目统计只有一次 Redis INCR，风险可控；若任务很重或必须可靠，应改成独立 MQ/Outbox，而不是继续扩大内存线程池。

## 七、性能测试

### 49. 异步下单到底优化了多少？

严格同条件的 1000 用户、1 秒爬坡、关闭限流测试中，接口平均响应从 345ms 降到 10ms，P95 从 619ms 降到 23ms，吞吐从 591.4/s 提升到 933.7/s。这里测的是接口受理，不是最终落库。

### 50. 简历中的 16.57ms 是什么？

它来自另一组 1000 用户、20 秒爬坡端到端脚本中的 POST 受理平均值，不能和 1 秒爬坡的 345ms 做严格 A/B。同一组端到端完成平均是 266.80ms，P95 1424ms，P99 2124ms。

### 51. 为什么端到端 P95 比平均值高很多？

少量尾部订单受 RabbitMQ 排队、消费者调度、数据库事务和 100ms 轮询间隔影响。平均值掩盖长尾，所以要同时报告 P95/P99，并用 queueDelay 和 dbProcess 分解。

### 52. 如何验证压测没有超卖？

不能只看 HTTP 成功率。要核对订单数、MySQL 库存、Redis库存、用户券重复分组、Pending/failed ZSet、RabbitMQ Ready/Unacked，并等待异步链路收敛后再下结论。

### 53. 现有压测最大不足是什么？

硬件、JVM、中间件资源、重复轮次和方差信息不完整，主要是本地对比基准。下一步应固定环境、分离压测机、重复多轮并同步采集 GC、线程池、Redis延迟、MQ队列和 MySQL 指标。

## 八、压力式追问

### 54. 如果 Redis 和 MySQL 库存不一致，以谁为准？

MySQL 是最终业务账本，Redis 是受理层库存。活动中优先靠 Redis 控流，后台通过订单、Pending 和失败恢复对账；发现异常不能盲目覆盖，应按订单事实重建 Redis 状态。

### 55. 如果 RabbitMQ 整体不可用，用户为什么还拿到 orderId？

因为资格已经在 Redis 原子预占，并持久登记 Pending。返回 orderId 表示受理，系统会重投；客户端通过状态接口看到 PROCESSING 或最终 FAILED。若产品要求 MQ 不可用时立即拒绝，则应在 Lua 前做健康门控，或者失败后同步恢复预占再返回失败，但两者有可用性与一致性取舍。

### 56. 如果 Outbox 永远失败怎么办？

重试达到上限后标记 DEAD，必须监控 DEAD 数量和最老事件年龄，修复依赖后人工或自动重置重放；Redis/Caffeine TTL 只是最终兜底，不能替代告警。

### 57. 如果要继续优化，优先做什么？

我会优先做三件事：统一和修正性能测试口径；给 Pending、Outbox、失败/停车队列建立可观测指标与告警；补齐跨实例热点缓存击穿保护和定期 Redis/MySQL 对账。它们比继续堆新中间件更能提高系统可信度。
