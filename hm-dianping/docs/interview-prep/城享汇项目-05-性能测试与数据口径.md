# 城享汇项目：05. JMeter 性能测试与数据口径

## 1. 阅读结论

项目保留了秒杀同步/异步对比、限流定位、二级缓存和秒杀端到端 JMeter 材料。最重要的面试原则是：**任何性能数字必须和线程数、Ramp-up、库存、限流开关、测量终点以及测试环境一起说。**

简历当前写法把两组不同场景中的 `345ms` 和 `16.57ms` 放在一起，不是严格 A/B 对比。推荐按本文第 7 节修正表达。

## 2. 指标定义

| 指标 | 含义 | 常见误区 |
|---|---|---|
| Average | 所有样本平均响应时间 | 容易掩盖长尾 |
| P95 | 95% 请求不超过该耗时 | 不是“最慢 5% 的平均值” |
| P99 | 99% 请求不超过该耗时 | 对抖动更敏感 |
| Throughput | 单位时间完成的请求数 | 受 Ramp-up、客户端和场景共同影响 |
| Error % | JMeter 认为失败的样本比例 | 业务拒绝若配置断言也会算错误，不一定是系统异常 |
| 受理耗时 | POST 秒杀到返回 orderId | 不含异步 MySQL 最终落库 |
| 端到端耗时 | 从发起下单到轮询观察到 COMPLETED | 包含 MQ 排队、事务和轮询误差 |

## 3. 同条件同步/异步对比

### 3.1 场景

```text
用户数/线程数：1000
Ramp-up：1 秒
库存：1000
限流：关闭
预热：已做
区别：Redis 预扣后，是请求线程同步写 MySQL，还是投递 RabbitMQ 后返回
```

### 3.2 结果

| 模式 | Average | P95 | P99 | Throughput | Error |
|---|---:|---:|---:|---:|---:|
| 同步下单 | 345ms | 619ms | 630ms | 591.4/s | 0% |
| RabbitMQ 异步受理 | 10ms | 23ms | 28ms | 933.7/s | 0% |

变化：

- 平均响应下降 335ms，约 97.1%。
- P95 下降 596ms。
- P99 下降 602ms。
- 吞吐量增加 342.3/s，约 57.9%。

### 3.3 能说明什么

异步模式把订单插入、MySQL 库存条件扣减和事务提交移出请求线程。请求线程只做限流（本组关闭）、Snowflake、Redis Lua 和 MQ 投递，因此接口受理明显变快。

### 3.4 不能说明什么

- 不能说明订单已经在 10ms 内落库。
- 不能说明系统端到端处理能力提升了同样比例。
- 不能说明 RabbitMQ 消除了数据库瓶颈；它只是缓冲和削峰，消费者最终仍要写数据库。
- 不能直接外推到生产硬件、集群或更高并发。

## 4. 端到端测试

### 4.1 JMeter 流程

`seckill-order-e2e.jmx` 对每个虚拟用户：

1. 从 CSV 读取独立 Token。
2. POST 秒杀接口并提取 orderId。
3. 按固定间隔请求状态接口。
4. 直到状态为 COMPLETED、FAILED、NOT_FOUND 或超时。
5. Transaction Controller 的父样本统计整个过程。

它测量“客户端何时观察到订单完成”，不是只测 POST。

### 4.2 场景与结果

```text
测试用户：1000
Ramp-up：20 秒
轮询间隔：100ms
入口限流：关闭
环境：本机 MySQL、虚拟机 Redis、Docker RabbitMQ
临时 Tomcat：max threads 500、accept-count 2000、max-connections 5000
```

| 指标 | 结果 |
|---|---:|
| 下单请求成功 | 1000/1000 |
| POST 受理平均耗时 | 16.57ms |
| 客户端端到端平均耗时 | 266.80ms |
| 客户端端到端 P95 | 1424ms |
| 客户端端到端 P99 | 2124ms |

端到端耗时包括：

- 秒杀请求本身。
- RabbitMQ 排队。
- 消费者事务落库。
- 状态查询请求。
- 最多约一个轮询间隔的观察误差。

### 4.3 为什么平均值 266.80ms，P95 却 1424ms

说明大多数订单很快完成，但末尾一部分订单受 MQ 排队、消费者并发度、数据库提交或调度抖动影响，形成明显长尾。只说平均值会掩盖用户尾部体验，因此简历同时给 P95 是有价值的。

### 4.4 服务端分段指标

Pending Hash 记录：

- `queueDelayMillis`：Redis 受理到消费者开始。
- `dbProcessMillis`：消费者开始到事务返回。
- `endToEndMillis`：Redis 受理到事务返回。

它们可以判断瓶颈是在 MQ 排队还是数据库事务。多实例时需要 NTP，因为这些时间点来自应用服务器时钟。

## 5. 秒杀正确性与限流测试

### 5.1 500 用户抢 500 库存，未限流

| Average | P95 | P99 | Throughput | 业务结果 |
|---:|---:|---:|---:|---|
| 6ms | 11ms | 14ms | 500.5/s | Redis/MySQL 库存为 0、订单 500、Pending 归零 |

### 5.2 900 用户抢 300 库存，未限流

| Average | P95 | P99 | Throughput | JMeter Error |
|---:|---:|---:|---:|---:|
| 6ms | 9ms | 12ms | 927.8/s | 66.67% |

66.67% 等于 600/900，报告将其解释为库存不足业务断言，而非系统异常。正确性应联合验证：

```text
订单数 = 300
Redis库存 = 0
MySQL库存 = 0
不存在重复(userId,voucherId)
Pending/队列最终归零
```

### 5.3 900 用户/1 秒，开启 300/s 限流

连接池与解析缓存优化后：

| 成功 | 限流 | Average | P95 | P99 | Throughput |
|---:|---:|---:|---:|---:|---:|
| 300 | 600 | 809ms | 1126ms | 1148ms | 629.8/s |

高延迟来自 900 个线程瞬时集中执行 Redis 滑动窗口脚本造成的排队，不代表所有限流场景都慢。

定位证据：

| 场景 | Average | P95 | P99 |
|---|---:|---:|---:|
| 300 用户/1 秒，阈值内 | 8ms | 13ms | 26ms |
| 900 用户/3 秒，平滑启动 | 6ms | 12ms | 17ms |

这也说明限流器本身需要容量评估；在保护下游之前，Redis 限流点可能先成为排队点。

## 6. Caffeine + Redis 热点测试

对 `GET /shop/1` 进行 1000 线程、每线程 100 次，共 100,000 请求：

| 场景 | Average | P95 | P99 | Max | Throughput | Redis GET 增量 |
|---|---:|---:|---:|---:|---:|---:|
| 关闭 Caffeine | 2ms | 3ms | 4ms | 18ms | 3297.3/s | 约 100,003 |
| 开启 Caffeine | 约 0ms | 1ms | 1ms | 11ms | 3320.8/s | 约 2 |

合理结论：

- 本地缓存显著减少 Redis 热点访问。
- P95/P99 和最大响应下降。
- 当前环境吞吐量仅提升约 0.7%，不能声称 QPS 大幅增长。
- JMeter 毫秒粒度显示 0ms，不代表真实耗时为零。

## 7. 简历数字的口径校正

### 7.1 当前简历表述

> 数据库同步 345ms 降至 16.57ms；端到端平均 266.80ms，P95 1.42s，1000 笔订单均成功落库且无超卖。

问题：

- 345ms 来自 1000 用户、1 秒 Ramp-up 的同步测试。
- 16.57ms 来自 1000 用户、20 秒 Ramp-up 的端到端测试中的 POST 受理时间。
- 两者负载形态不同，不能作为严格对照。

### 7.2 推荐简历表述

> 使用 JMeter 对秒杀链路进行同步/异步与端到端验证：在关闭入口限流、1000 用户 1 秒爬坡的同条件测试中，RabbitMQ 异步受理将接口平均响应由 345ms 降至 10ms，P95 由 619ms 降至 23ms，吞吐量由 591.4 req/s 提升至 933.7 req/s；在另一组 1000 用户、20 秒爬坡的端到端测试中，订单完成平均 266.80ms、P95 1.424s，最终 1000 笔订单落库且库存一致。

### 7.3 如果不能修改简历，面试时如何解释

> 简历为了压缩篇幅把两个测试结果放在了一句里。严格来说，345ms 对应的是 1000 用户 1 秒爬坡的同步基线；同条件异步结果是 10ms。16.57ms 是另一组 20 秒爬坡端到端脚本里的下单受理平均耗时，而该组真正的订单完成平均值是 266.80ms。我在详细复盘时会把这两个口径分开。

主动澄清比坚持不准确对比更可信。

## 8. 测试环境限制

现有报告没有完整记录：

- CPU、内存、操作系统细节。
- JVM 参数与 GC 数据。
- JMeter 版本在所有报告中的统一记录。
- MySQL、Redis、RabbitMQ 的详细资源限制与监控曲线。
- 多轮重复试验的方差和置信区间。
- JMeter 是否与服务部署在同机导致资源竞争。

所以这些结果适合作为本地方案对比和回归基准，不应包装成生产容量承诺。

## 9. 如何证明“无超卖且全部落库”

性能指标之外还要查业务不变量：

```sql
-- 订单总数应等于成功受理且最终完成的用户数
SELECT COUNT(*) FROM tb_voucher_order WHERE voucher_id = ?;

-- 不应有一人多单
SELECT user_id, voucher_id, COUNT(*) c
FROM tb_voucher_order
WHERE voucher_id = ?
GROUP BY user_id, voucher_id
HAVING c > 1;

-- MySQL库存不能为负，并与预期一致
SELECT stock FROM tb_seckill_voucher WHERE voucher_id = ?;
```

同时检查：

```text
Redis 秒杀库存
Pending ZSet / failed ZSet
RabbitMQ Ready / Unacked
JMeter COMPLETED / FAILED / timeout 数量
```

只有延迟、吞吐和业务不变量同时满足，测试才完整。

## 10. 推荐的下一轮压测

1. 固定硬件与中间件资源，同步和异步采用相同线程、Ramp-up、库存及预热。
2. 每种场景至少重复 5 次，报告均值、标准差和最差轮次。
3. JMeter 与服务分机部署，排除客户端抢 CPU。
4. 同步采集 JVM GC、Tomcat 线程池、Redis 延迟、RabbitMQ队列深度、消费者速率、MySQL连接池与慢 SQL。
5. 分别报告“接口受理”“服务端落库”“客户端观察完成”。
6. 增加故障注入：RabbitMQ 暂停、错误 routing key、消费者异常、Redis 短暂不可用。
7. 压测结束后自动执行库存、订单唯一性、Pending 和队列收敛断言。
